# 応募書類の判定（Winスクール講師）

書類に書かれている事実だけを根拠に、機械的に判定する。

## なぜ手順を固定するのか

同じ候補者を何度見ても同じ結論になることが、この判定では一番重要になる。採用担当者は判定結果だけを見て次のアクションを決めるので、根拠が示されていない判定や、前回と食い違う判定は使えない。

そのため、**各軸を独立に判定してから、総合判定は判定表のとおりに導く**という順序を守る。先に「なんとなく良さそう / 厳しそう」と結論を決めてから理由を後付けすると、軸の境界が曖昧になって再現しなくなる。

迷いが生じるのは**軸ごとの判定のとき**で、そこでは推測で落とさず △ に倒す。一方**総合判定では迷わない**。3軸が出た時点で答えは判定表で一つに決まる。この2つを混同しないこと。

## 募集中の3求人

すべて Winスクール 京都駅前校 / 業務委託 パソコンスクール講師。分野だけが異なる。

| ID | 求人名 | 対象ツール・分野 |
|---|---|---|
| `cad` | CAD講師 | AutoCAD / Jw_cad / Vectorworks / Revit / SolidWorks / CATIA |
| `web` | Webデザイン講師 | Illustrator / Photoshop / HTML/CSS / JavaScript / Premiere Pro |
| `it` | プログラミング（IT）講師 | Java / Python / C言語 / SQL / ネットワーク / Linux / AWS / Power BI / Power Automate / Excel VBA |

求人側の応募資格は「**講師経験不問**」「下記いずれかの実務経験をお持ちの方（**経験年数は問わない**）」。
したがって講師経験の有無も実務年数の長短も、それ自体では判定を動かさない。

## 軸1：年齢

**54歳以下は ◯ / 55〜70歳は △ / 71歳以上は ×**

年齢が読み取れない場合は **△**。推測しないこと。卒業年度からの逆算は、浪人・留年・編入で簡単に数年ずれるので根拠にしない。

生年月日と年齢の両方が書いてあるなら、**生年月日から今日の日付で計算した満年齢を採用する**。書類作成から時間が経っていて、記載年齢が古くなっていることがあるため。**この差は「書類の食い違い」ではない**ので、要確認に落とす理由にはしない（1歳ずれるのは当然に起きる）。

今日の日付が分からない状況では、記載されている年齢をそのまま使い、懸念点に「年齢は書類記載値」と書く。境界（54/55、70/71）にかかる年齢のときだけ、この一言が効いてくる。

55歳以上を △ にしているのは、採用側が「上限70歳以内だが一応知っておきたい」という位置づけで見ているから。**△は不合格の予備軍ではなく、担当者に判断を渡す印**として扱う。

## 軸2：求人適合

3求人のうち**どれか1つでも当てはまれば ◯**。3つ全部を評価する必要はない。

- **◯** … 上の表にある対象ツール・分野の経験が書類から明確に読み取れる
- **△** … 対象ツールと**同じ系統の別製品・別言語**の経験がある（例：Fusion 360 や AutoCAD LT 以外の3D CAD、PHP や Ruby などの表にない言語、Figma や XD などの表にないデザインツール）
- **×** … 上のどちらにも当てはまらない

△ は「**3求人のいずれかの分野の中での**別製品・別言語」に限る。分野そのものが違えば △ にはならない。

**事務職としての一般的なPC利用は ×** にする。Word・Excel の基本操作、業務システムへの入力、社内資料の作成、メール・グループウェアの利用などは、どの分野の「同じ系統」にも入らない。これらを △ で拾い始めると、PCを使う仕事の経験者が全員 △（=要確認）になって、担当者に判断を丸投げすることになる。本人が「専門的なソフトの経験はありません」「未経験の分野です」と書いている場合も、それを裏づける記載として扱う。

**業種固有の業務パッケージソフトも ×**。介護記録ソフト、電子カルテ、会計ソフト、POS、医療事務システム、CRM などは、専門ソフトではあっても3求人のどの分野でもない。「表に無い専門ソフトだから △」と拾うと、あらゆる業種の経験者が △ になって上と同じことが起きる。経歴サマリに「関連スキル」として書いて、担当者には見えるようにしておく。

`Excel VBA` は製品＋機能まで指定された対象ツールなので、**マクロ・VBA を書いた記述が無い Excel は該当しない**。関数を使った集計やシフト表の作成は、どれだけ年数が長くても × 側。スキル欄に「Excel（関数・簡単なマクロ）」と添えてあるだけの場合も該当させない。業務として VBA で何を作ったかが書かれているときに限って該当とする。程度の分かる記述が無いものを拾うと、Excelを使う事務職が `it` 求人に該当し始める。

**◯ の根拠として挙げてよいのは、上の表に実際に載っている名称だけ**。「Fusion 360 があるから CAD 分野に該当」と言い換えて ◯ にすると、後から見返したときに判定の根拠を追えなくなる（Fusion 360 は △ 側）。表にない名称は経歴サマリに「関連スキル」として書く。

ただし表の項目が**カテゴリ名**（`SQL` / `ネットワーク` / `Linux` / `AWS`）の場合は、その配下の具体的な製品名も ◯ の根拠として扱ってよい。Oracle・SQL Server は `SQL`、EC2・RDS・S3 は `AWS`、CentOS・RHEL は `Linux`。カテゴリ名で書かれているのは製品を限定しない意図だから。

この軸では**実務かどうかを問わない**。学習・職業訓練で触っただけでも、対象ツールの経験があるなら ◯ でよい。実務かどうかは軸3で見る。ここで両方を混ぜると、軸3と二重に減点することになる。

### 想定求人の選び方

複数の求人に該当しうる場合は、**実務経験がいちばん濃い分野を「想定求人」として1つ選ぶ**。担当者はこの1行を見て、どの求人の面接に回すかを決めるため。実務がどれも同程度なら、経験年数が長い方を選ぶ。

選ばなかった側も該当するなら、経歴サマリに「◯◯講師にも該当しうる」と1行添える。担当者が別枠で検討できるようにしておく。

求人適合が × のときは、想定求人の欄に「該当なし」と書く。

## 軸3：実務経験

**軸2で選んだ想定求人の分野**について、**業務としての使用経験**があるか。年数は問わない。

この軸は根拠が重なりやすい（学習と無償制作と本人の申告が同じ書類に混在する）ので、**上から順に当てはめ、最初に当てはまった行で決める**。

| 順 | 条件 | 判定 |
|---|---|---|
| 1 | 軸2が × | **×** |
| 2 | 本人が、その分野の実務経験が無いと書いている | **×** |
| 3 | その分野の対象ツールのうち、どれか1つでも職歴の業務内容として使っていた | **◯** |
| 4 | 継続的に受託していた、業務として納品していたと読める | **◯** |
| 5 | 上のどれにも当てはまらない（学習・職業訓練・資格取得・無償制作・個人開発のみ、または実務か判別できない） | **△** |

**2行目が3行目より先に来るのが要点**。本人が「デザインの実務経験はありません」と書いていて、なおかつ無償制作や学習歴がある書類は珍しくない。そこで「無償制作があるから △」を先に適用すると、本人がはっきり否定している経験を、こちらが勝手に格上げすることになる。**本人の申告がいちばん確かな情報**なので先に見る。「〜は実務ではないが」「独学の範囲にとどまる」のような言い方も、この行に含める。

逆に本人が何も書いていなければ、無償制作だけを根拠に実務ありとはしない（5行目の △）。

1行目は、評価する分野そのものが無い状態。何を実務経験とみなすかの基準が無いまま ◯ を付けると、事務職の Excel 実務20年が「実務経験 ◯」として表に残り、表だけ見た担当者に誤解を与える。

3行目について、分野の中で一部のツールだけ実務がある状態（例：HTML/CSS は実務、Illustrator は学習のみ）は ◯ でよい。求人が「いずれかの実務経験」を求めているので、ここで全ツールを要求すると求人より厳しくなる。実務がないツールについては懸念点に書いて、担当者に見えるようにする。

**軸2が △ のとき**は、△の根拠にした関連スキル（同系統の別製品・別言語）について同じ表を当てはめる。対象ツールそのものが無いことは軸2で既に減点済みなので、ここで重ねて引かない。

## 総合判定

3軸が出そろってから、この表で上から順に当てはめる。最初に当てはまった行で決まる。

| 順 | 条件 | 総合判定 |
|---|---|---|
| 1 | 追加の判定条件の【不合格】に該当した | **不合格** |
| 2 | 3軸に × が1つでもある | **不合格** |
| 3 | 3軸すべて ◯ かつ 追加の判定条件の【懸念】に該当しない | **合格** |
| 4 | それ以外（△を含む、または【懸念】に該当、×は無い） | **要確認** |

「◯◯△だから惜しい」といった調整はしない。表のとおりに決める。判定の一貫性はここで担保される。

**△が1つでもあれば要確認になる**。軸1で「△は不合格の予備軍ではない」と書いたのは不合格にするなという意味で、合格にしてよいという意味ではない。55歳以上の候補者は他の2軸が完璧でも要確認になる。それが「上限70歳以内だが一応知っておきたい」という採用側の位置づけに対応する扱いで、担当者が見て問題なければそのまま進めることになる。

## 追加の判定条件

**有効な条件は、次の「有効な条件」の下に書かれている行だけ**。この節の書き方の説明や例文は判定に使わない。説明文を条件として適用すると、担当者が設定していない条件で落とすことになる。

### 有効な条件

（未設定）

### 書き方（ここは判定に使わない）

「有効な条件」の下に1行ずつ書き足す。頭に次のどれかを付ける。

- `【不合格】` … 当てはまったら不合格にする
- `【懸念】` … 当てはまったら懸念点に書き、3軸が全部◯でも要確認に落とす
- `【補足】` … 判定の参考にするだけ（判定は変えない）

書き方の例（**これらは有効な条件ではない**）：`【不合格】普通自動車免許を持っていない` / `【懸念】直近3年以内に1年以上の離職期間がある` / `【補足】資格の有無より実務での使用年数を重視する`

条件が設定されている場合、**書類から該当するか判断できないものは、不合格にせず要確認に倒す**。「〜が無い」ことは書類に書かれないので、読み取れないことを根拠に落とすと誤判定になる。

## 出力形式

下の形で返す。項目を減らしたり順序を変えたりしないこと。担当者は複数人分を並べて見るので、形が揃っていないと比較できなくなる。

**以下は書式の見本であり、判定の先例ではない。** 総合判定は必ず上の判定表から導く。見本の見出しと表が矛盾して見えるときは、判定表が正しい。

```

### 懸念点

- Illustrator・Photoshop は職業訓練のみで、実務での使用記載が無い
- 勤務可能日は週2〜3日・10時〜16時（夜間不可）と記載

### 経歴サマリ

Illustrator・Photoshop・HTML/CSSを習得、関連資格も取得。関連スキルとして

```

合格の場合も同じ形。下の見本に懸念点が無いのは書くことが無かったからで、**合格でも書くことがあれば懸念点の節は付ける**（勤務可能日の記載など）。懸念点の有無は総合判定を動かさない。

```
## 判定：合格

**（氏名）**（45歳）／ 想定求人：CAD講師

| 軸 | 判定 | 根拠 |
|---|---|---|
| 年齢 | ◯ 45歳 | 1981年3月14日生（履歴書） |
| 求人適合 | ◯ | AutoCAD / Jw_cad / Revit |
| 実務経験 | ◯ | 「AutoCADによる施工図作成」（設計事務所・職務経歴書） |
```

### 各欄の書き方

**年齢の欄**は、判定の記号と満年齢を並べる（`◯ 45歳` / `△ 58歳` / `× 72歳` / `△ 不明`）。

**求人適合の欄**は、該当した対象ツールの名称をスラッシュ区切りで並べる。ここは引用ではなく一覧で構わない。表にある名称と一致しているかを担当者が一目で確かめられることが目的なので、文章にすると逆に読みにくくなる。× のときは並べる名称が無いので `（3求人の対象ツールの記載なし）` と書く。

**実務経験の欄**は、**書類中のいちばん強い記述を1つだけ短く引用し、出どころを括弧で添える**。要約すると判定が正しいかを担当者が確認できなくなる。一方で引用を並べすぎると表の幅が崩れて、複数人を並べて見られなくなる。補足が必要なら懸念点か経歴サマリに回す。

**記載が無いことが判定の根拠になる場合**（△ や × のとき）は、引用できるものが無いので `（AutoCAD の記載なし）` のように括弧書きで示す。無い事実を引用しようとして、書類に無い文を作らないこと。

**懸念点**は、担当者に伝えておきたい事実を書く欄で、**それ自体が総合判定を動かすことはない**（追加の判定条件の【懸念】に該当した場合だけは判定表の4行目で要確認になる）。合格に懸念点が付くのは矛盾ではない。書く対象は次のようなもの。

- 軸の判定に使った事実の補足（実務が一部のツールに限られる、など）
- **1年以上**の職歴の空白期間（それより短い期間は書かない。転職や退職後の応募では普通に生じるため）
- 勤務可能日・勤務時間の記載（求人側の必要シフトは分からないので、「制約」と決めつけず記載内容をそのまま伝える）
- 書類の欠落、書類間の食い違い

無ければ「### 懸念点」ごと省略してよい。

**経歴サマリ**は3〜5行。職歴の通算年数、判定に関係した経験、対象ツール以外の関連スキル、他の求人にも該当しうる場合はその一言を入れる。書類が薄くて書けることが少なければ短くてよいが、節ごと省略はしない。

## 読み取るときの注意

**書かれていないことを推測で補わない。** 読み取れない項目は不明として扱い、△ にする。書類選考で一番避けたいのは、推測で落としてしまうこと。

**評価の根拠にしない属性**：性別、国籍、家族構成、健康状態、信条、顔写真の印象。年齢は求人側の要件として明示されているため軸1で扱うが、それ以外の属性は判定に持ち込まない。

**この除外は懸念点にも及ぶ。** 懸念点は担当者の判断材料になるので、そこに書けば結局これらの属性で選考することになる。介護・育児・体調が勤務条件の背景として書かれていても、事情そのものは書かず、勤務可能日・勤務時間の記載だけを書く。転職理由として健康上の事情が書かれている場合も、書かない。

**書類が一部しか無い場合**（履歴書だけ、職務経歴書だけ等）は、読み取れた範囲で判定し、懸念点に「職務経歴書が未提出」のように書く。書類が足りないことを理由に不合格にはしない。

**複数の書類で内容が食い違う場合**は、その旨を懸念点に書いて要確認に落とす。氏名が違う場合は添付の取り違えの可能性があるので必ず指摘する。ただし記載年齢と生年月日から計算した年齢の1歳程度のずれは食い違いに含めない（軸1に書いたとおり）。

**スキルシート形式**（得意分野・得意業務・スキル一覧が表になっているもの）も同じ手順で判定する。スキル一覧に並んでいるだけの技術は、職歴欄で業務として使った記述と結びつかない限り軸3の ◯ にはしない。
